Prezentarea conceptului teoretic

Ce este POLIMORFISMUL DINAMIC?!

Din greacă ("multe forme"), reprezintă capacitatea unui obiect de a fi tratat ca o instanță a clasei sale de bază, păstrându-şi în acelaşi timp comportamentul specific.

Noțiuni de bază:

Moștenirea

Creăm o clasă de bază cu proprietățile generale, iar subclasele le moștenesc direct, putând apoi să vină cu propriile lor completări.

Suprascrierea

E momentul în care o clasă derivată își personalizează comportamentul, suprascriind o metodă virtuală moștenită de la clasa de bază.

Upcasting

Atunci când rulează programul, putem să tratăm un obiect din clasa copil exact ca și cum ar fi un obiect din clasa părinte, dar el își păstrează comportamentul lui specific.

Rolul și Importanța:

Polimorfismul dinamic e baza unui principiu important în programare: ne permite să adăugăm funcționalități noi în cod fără să fim nevoiți să spargem sau să modificăm ce am scris deja și funcționează. Astfel:
  • Nu mai legăm clasele strâns: Dacă modifici ceva într-o parte, nu se mai strică totul în restul programului.
  • Adăugăm funcții noi fără riscuri: Doar scriem o clasă nouă, fără să atingem sau să strici codul vechi care deja funcționează.
  • Reutilizăm codul mult mai bine: O singură funcție generală poate gestiona mai multe tipuri de obiecte, fără să scriem cod repetitiv.

Caracteristici principale:

Formatul

Metoda din clasa-copil trebuie să fie copia a celei din clasa părinte: să aibă exact același nume, aceleași argumente și să întoarcă același tip de rezultat.

Cuvinte Cheie

în clasa de bază punem virtual sau abstract, iar în clasa derivată folosim obligatoriu override ca să-i facem rescrierea. (C#)

Ierarhie

Polimorfismul dinamic nu funcționează singur, are nevoie de o relație de moștenire. Trebuie să avem o structură clară de tip părinte-copil între clase.
Explicarea modului de utilizare

Situații Practice de Aplicare:

Metode de plată (card, PayPal, crypto) — toate trebuie să execute, dar diferit.

Figuri Geometrice Cerc, dreptunghi, triunghi — toate au arie, dar cu formule diferite.

Sistem de Notificări Email, SMS — trimit un mesaj, dar prin căi diferite.

Animale Câine, pisică, pasăre — toate fac sunet, dar fiecare scoate alt sunet.

Autentificare telefon Deblochezi telefonul — cu parolă, amprentă sau Face ID. Telefonul nu știe dinainte ce metodă folosești, dar toate fac același lucru: "verifică identitatea".

Aplicație de navigație Utilizatorul alege mijlocul de transport — mașină, bicicletă, mers pe jos. Aplicația calculează ruta diferit pentru fiecare, dar interfața e aceeași: "calculează rută".

Avantaje și Dezavantaje:
Avantaje Dezavantaje
Poți adăuga clase noi fără să modifici codul existent. Dacă ai prea multe clase una peste alta, devine greu de urmărit.
Abstracție înaltă — lucrezi cu interfețe, nu cu implementări concrete. Poate fi complicat pentru începători să înțeleagă ce se întâmplă în spate.
Codul este modular — fiecare clasă are responsabilitatea ei clară. Dacă clasa de bază se schimbă, toate clasele derivate pot fi afectate.
Reduce duplicarea — comportamentul comun e scris o singură dată în clasa de bază. Necesită planificare atentă a ierarhiei de clase de la început.
Exemple Practice

Fragmente de cod:
Metodă plata: 

class Plata {
    public virtual void Proceseaza() { }
}
class Card : Plata {
    public override void Proceseaza() { Console.WriteLine("Platesc cu cardul"); }
}
class PayPal : Plata {
    public override void Proceseaza() { Console.WriteLine("Platesc cu PayPal"); }
}
Explicație:
Clasa Plata definește o metodă generală Proceseaza() marcată cu virtual, pe care clasele Card și PayPal o moștenesc și o suprascriu cu override, fiecare cu propriul mesaj. Când creăm un obiect de tip Card sau PayPal și apelăm Proceseaza() , programul decide singur la rulare ce versiune a metodei să execute, în funcție de tipul real al obiectului. Astfel, putem adăuga oricând o nouă metodă de plată fără să modificăm codul existent.
Figuri geometrice: 
class Figura {
    public virtual float Arie() { return 0; }
}
class Cerc : Figura {
    float r;
    public override float Arie() { return 3.14f * r * r; }
}
class Dreptunghi : Figura {
    float l, h;
    public override float Arie() { return l * h; }
}
Explicație:
Clasa Figura definește o metodă generală Arie() marcată cu virtual, pe care clasele Cerc și Dreptunghi o moștenesc și o suprascriu cu override, fiecare folosind propria formulă matematică — 3.14 * r * r pentru cerc și l * h pentru dreptunghi. Când apelăm Arie() pe un obiect, programul știe automat la rulare ce formulă să aplice în funcție de tipul real al figurii. Astfel, putem adăuga oricând figuri noi fără să modificăm codul existent.

Explicație:
Clasa Notificare definește o metodă generală Trimite() marcată cu virtual, pe care clasele Email și SMS o moștenesc și o suprascriu cu override, fiecare trimițând mesajul prin canalul ei specific.

Când apelăm Trimite() pe un obiect, programul știe automat la rulare ce canal să folosească în funcție de tipul real al notificării.

Astfel, putem adăuga oricând metode noi de notificare, precum Push sau WhatsApp, fără să modificăm codul existent.
Cont Bancar: 
class ContBancar {
    public string Titular;
    public double Sold;
    public virtual void Retrage(double suma) { }
    public virtual void AplicaDobanada() { }
}
class ContCurent : ContBancar {
    public override void Retrage(double suma) {
        Sold -= suma;
        Console.WriteLine($"{Titular} a retras {suma} Lei. Sold ramas: {Sold} Lei");
    }
    public override void AplicaDobanada() {
        Console.WriteLine("Cont curent: fara dobanda");
    }
}
class ContEconomii : ContBancar {
    public override void Retrage(double suma) {
        if (suma > Sold * 0.5) {
            Console.WriteLine("Nu poti retrage mai mult de 50% din economii!");
        } else {
            Sold -= suma;
            Console.WriteLine($"Retras {suma} lei din economii. Sold: {Sold} Lei");
        }
    }
    public override void AplicaDobanada() {
        double dobanda = Sold * 0.05;
        Sold += dobanda;
        Console.WriteLine($"Dobanda 5% aplicata: +{dobanda} Lei. Sold nou: {Sold} Lei");
    }
}
Explicație:
Clasa ContBancar definește metodele generale Retrage() și AplicaDobanda() marcate cu virtual, pe care clasele ContCurent și ContEconomii le moștenesc și le suprascriu cu override, fiecare cu propriile reguli.

ContCurent permite retragerea oricărei sume fără dobândă, pe când ContEconomii blochează retragerea dacă depășește 50% din sold și aplică o dobândă de 5%.

Astfel, același apel Retrage() se comportă diferit în funcție de tipul real al contului, fără să fie nevoie să verificăm manual ce tip de cont avem.
Angajați: 
class Angajat {
    public string Nume;
    public virtual double CalculeazaSalariu() { return 0; }
}
class AngajatSimplu : Angajat {
    double salaruiBaza = 5000;
    public override double CalculeazaSalariu() {
        Console.WriteLine($"{Nume} primeste salariu fix: {salaruiBaza}Lei");
        return salaruiBaza;
    }
}
class Freelancer : Angajat {
    int oreLucrate;
    double tarifOrar = 100;
    public override double CalculeazaSalariu() {
        double total = oreLucrate * tarifOrar;
        Console.WriteLine($"{Nume} a lucrat {oreLucrate}h x {tarifOrar} = {total} Lei");
        return total;
    }
}
class Consultant : Angajat {
    double vanzari;
    public override double CalculeazaSalariu() {
        double total = vanzari * 0.15;
        Console.WriteLine($"{Nume} comision 15% din {vanzari} = {total} Lei");
        return total;
    }
}
Explicație:
Clasa Angajat definește o metodă generală CalculeazaSalariu() marcată cu virtual, pe care clasele AngajatSimplu, Freelancer și Consultant o moștenesc și o suprascriu cu override, fiecare calculând salariul după regula ei.

AngajatSimplu primește mereu același salariu de 5000 Lei, Freelancer este plătit în funcție de orele lucrate înmulțite cu tariful orar, iar Consultant câștigă 15% din vânzările realizate.

Astfel, același apel CalculeazaSalariu() produce rezultate complet diferite în funcție de tipul real al angajatului, fără să verificăm manual ce tip este.
Vehicule: 
class Vehicul {
    public string Model;
    public virtual double CalculeazaConsum(double km) { return 0; }
}
class Masina : Vehicul {
    public override double CalculeazaConsum(double km) {
        double consum = km * 0.07;
        Console.WriteLine($"{Model} consuma {consum}L pentru {km}km");
        return consum;
    }
}
class ElectricCar : Vehicul {
    public override double CalculeazaConsum(double km) {
        double kwh = km * 0.2;
        Console.WriteLine($"{Model} consuma {kwh}kWh pentru {km}km");
        return kwh;
    }
}
Explicație:
Clasa Vehicul definește o metodă generală CalculeazaConsum() marcată cu virtual, pe care clasele Masina și ElectricCar o moștenesc și o suprascriu cu override, fiecare calculând consumul după unitatea ei specifică.

Masina calculează consumul în litri de combustibil — 7L la 100km, pe când ElectricCar calculează consumul în kilowați-oră — 0.2 kWh per km.

Astfel, același apel CalculeazaConsum() returnează rezultate diferite în funcție de tipul real al vehiculului, fără să verificăm manual ce tip este.

Exemplu personal:

 
class Dezastru {
    public string Locatie;
    public int NrPersoane;
    public virtual void Alerteaza() { }
    public virtual void Evacueaza() { }
    public virtual int CalculeazaTimp() { return 0; }
}

class Cutremur : Dezastru {
    public double Magnitudine;
    public override void Alerteaza() {
        Console.WriteLine($"CUTREMUR {Magnitudine} grade la {Locatie}! Iesiti din cladiri!");
    }
    public override void Evacueaza() {
        Console.WriteLine($"Evacuare {NrPersoane} persoane din {Locatie} — adaposturi deschise.");
    }
    public override int CalculeazaTimp() {
        int minute = (int)(Magnitudine * 3);
        Console.WriteLine($"Timp estimat evacuare: {minute} minute");
        return minute;
    }
}

class Inundatie : Dezastru {
    public double NivelApa;
    public override void Alerteaza() {
        Console.WriteLine($"INUNDATIE la {Locatie}! Nivel apa: {NivelApa}m. Urcati la etaje superioare!");
    }
    public override void Evacueaza() {
        Console.WriteLine($"Evacuare {NrPersoane} persoane cu barci. Zonele joase din {Locatie} blocate.");
    }
    public override int CalculeazaTimp() {
        int minute = (int)(NivelApa * 10 + 20);
        Console.WriteLine($"Timp estimat evacuare: {minute} minute");
        return minute;
    }
}

class Incendiu : Dezastru {
    public int EtajAfectat;
    public override void Alerteaza() {
        Console.WriteLine($"INCENDIU la etajul {EtajAfectat} in {Locatie}! Sunati 112!");
    }
    public override void Evacueaza() {
        Console.WriteLine($"Evacuare {NrPersoane} persoane pe scari de urgenta. Lifturile blocate in {Locatie}.");
    }
    public override int CalculeazaTimp() {
        int minute = EtajAfectat * 2 + 5;
        Console.WriteLine($"Timp estimat evacuare: {minute} minute");
        return minute;
    }
}

Concluzii

Observații personale

Am observat că prin folosirea polimorfismului dinamic dispar acele liste infinite de verificări (if-uri), iar codul devine mult mai scurt, mai curat și mai ușor de citit.

Codul care dă comanda generală nu trebuie să cunoască detaliile tehnice ale fiecărui obiect în parte; fiecare componentă își gestionează singură logica internă, fără să le încurce pe celelalte.

Când este nevoie de o funcționalitate nouă în program, aceasta poate fi adăugată sub formă de piesă separată, fără a modifica sau a risca să stricăm codul care funcționează deja.

Programul nu mai este „bătut în cuie" de la început; el devine capabil să ia decizii corecte în ultima secundă, în funcție de ce alege sau ce introduce utilizatorul în aplicație.

Acest mecanism ne permite să scriem codul așa cum gândim în viața de zi cu zi — dăm o singură comandă generală, iar acțiunea se adaptează natural în funcție de obiectul vizat.

Dificultăți întâlnite

Confuzia dintre suprascriere (override) și supraîncărcare (overload): Tendința greșită de a schimba parametrii din paranteze când, de fapt, polimorfismul dinamic cere păstrarea exactă a aceleiași semnături a metodei în clasa copil.

Rigiditatea semnăturii metodei: O singură literă greșită sau un parametru în plus anulează polimorfismul dinamic; sistemul nu mai vede suprascrierea (override), ci consideră că ai creat o metodă complet nouă.

Obligația de a redefini constructorii: Deși clasele copii moștenesc metodele, ele nu moștenesc constructorii; este necesar un efort suplimentar pentru a scrie constructori noi în fiecare copil și pentru a apela manual părintele (prin base).

Importanța în Dezvoltarea Aplicațiilor Software
Arhitectură de tip Plugin: Permite adăugarea de noi funcționalități ca module detașabile, fără ca aplicația de bază să cunoască detaliile lor tehnice.
Abstragerea complexității: Trimite o singură comandă generală (ex: Conecteaza()), lăsând polimorfismul dinamic să execute în spate detaliile tehnice specifice fiecărei tehnologii.
Respectarea Principiului Open-Closed: Permite extinderea comportamentului aplicației prin clase noi, lăsând codul vechi neatins și protejat de bug-uri.
Eliminarea Datoriei Tehnice: Șterge verificările repetitive din cod; când apare un obiect nou, nu mai trebuie să modifici zeci de fișiere existente.

Concluzii Finale

Polimorfismul dinamic transformă programele din secvențe rigide în ecosisteme adaptabile. Stăpânirea acestui concept este pasul decisiv de la un simplu scriitor de cod la un arhitect software.
